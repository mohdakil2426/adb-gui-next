## 1. Critical defects (correctness & safety)

These are ranked above performance because they can brick a user's device, abort the process, or silently corrupt output.

### 1.1 The destructive-action risk model is inverted

`fastboot flash` writes an arbitrary user-selected `.img` to an arbitrary **free-text** partition name and executes **with no confirmation whatsoever**:

- `FlasherView.tsx:156` → `useFlasherActions.ts:157` → `:69 FlashPartition(...)`
- `userdata` and `super` are offered as first-class autocomplete suggestions (`FlasherView.tsx:33`)

Meanwhile `Wipe Data`, 200 px below it on the same screen and fully recoverable, sits behind a complete `AlertDialog` ("Are you absolutely sure?", `DangerZoneCard.tsx:38-67`).

**Worse — flashes auto-fire on cable insertion.** Clicking Flash with no device attached *queues* the action and shows `Waiting for Device…`; the flash then executes the moment a fastboot device appears (`useFlasherActions.ts:102-129`, label at `FlasherView.tsx:166`). A destructive write triggered by plugging in a USB cable. File paths also persist to `localStorage` indefinitely (`useFlasherActions.ts:24-37`), so a stale path can be pre-loaded into that button days later.

**Confirmation coverage is inconsistent app-wide:**

| Confirmed | Unconfirmed |
| --- | --- |
| Wipe ×2, uninstall ×2, file delete | **flash**, **sideload**, **slot switch**, `adb kill-server`, reboot→bootloader/recovery, AVD ramdisk restore, cache clear |

Slot switching (`--set-active=a/b`) fires immediately (`FastbootUtilitiesPanel.tsx:102,113`); switching to an unpopulated slot is a soft-brick.

### 1.2 Debloat has no undo path — the safety net is unreachable

`restore_debloat_backup` is fully implemented in Rust (`commands/debloat.rs:240`), registered (`lib.rs:141`), and permitted (`permissions/autogenerated.toml:84,162`) — but there is **no wrapper in `src/desktop/backend.ts` and no caller anywhere in `src/`**.

The UI creates backups and tells the user so (`ReviewSelectionDialog.tsx:65-66`), then offers no way to restore them. The app's most dangerous everyday feature presents itself as reversible and is not.

### 1.3 A malformed remote payload can hard-abort the process

`payload/remote/mod.rs:951-957` with `Cargo.toml:151` (`panic = "abort"`):

```rust
let data_offset_op = operation.data_offset.unwrap_or_default() as usize;  // untrusted
let data_length    = operation.data_length.unwrap_or_default() as usize;  // untrusted
let data_end = data_offset.saturating_add(data_offset_op) + data_length;  // UNCHECKED +
if data_end > mmap.len() { anyhow::bail!(...) }
let raw_data = &mmap[data_offset + data_offset_op..data_end];             // UNCHECKED +
```

`overflow-checks` is off in release, so the second add **wraps** to a small value that passes the bounds check, and the slice index then panics. With `panic = "abort"` that is an immediate `SIGABRT` of the whole application, reachable from a URL the user pasted.

The same overflow at `crau/extract.rs:265` lands *inside* bounds instead — no panic, but the extractor reads the wrong region and writes a **silently corrupt image**. Only optional L3/L4 SHA-256 catches it.

### 1.4 >4 GB OTA ZIPs are broken; deflated payloads OOM

Two independent ZIP central-directory parsers exist with divergent correctness. `http_zip.rs:153-196` reads `cd_offset` as a bare `u32` and never applies ZIP64 extra fields, so any ZIP ≥ 4 GiB — i.e. **most full OTA packages** — reads the `0xFFFFFFFF` sentinel and computes garbage. `factory.rs:321-352,422-463` implements ZIP64 correctly.

Separately, `read_payload_from_zip` (`http_zip.rs:306-340`) downloads and inflates the *entire* member into two `Vec`s before returning a slice — and it is called from `list_remote_payload_partitions`, which only needs the first 1 MiB header. Merely **listing partitions** on a deflated 4 GB payload downloads 4 GB and allocates ~9 GB.

### 1.5 `NonTemporalWriter` is broken on shipped targets

`payload/io/write.rs:40-66`:

- `MmapMut::map_mut` on a zero-length file always errors, and callers pass `size.unwrap_or(0)` (`extract.rs:117`, `remote/mod.rs:671,835`) — any partition lacking size metadata fails outright.
- On the shipped `i686-pc-windows-msvc` target (`publish.yml:171`), `usize` is 32-bit: `offset as usize` truncates and >2 GiB outputs cannot be mapped. **Payload extraction is fundamentally broken on the 32-bit artifacts.**
- Growth policy `max(needed, len*2)` doubles the output file and never truncates back.

## 2. Performance — frontend

### 2.1 Every log line re-renders the entire application

`MainLayout.tsx:52` subscribes to `unreadCount`, which `logStore` increments on **every** log while the panel is closed — and closed is the default (`logStore.ts:44,64`). Because `renderContent` is an inline arrow (`MainLayout.tsx:196`) and neither `ViewContent` nor any view is memoised, one log line re-renders the **entire active view subtree** plus `Header` → `DeviceSwitcher`, `AppSidebar`, and `BottomPanel`.

There are **100 log-emitting call sites** funnelling through `errorHandler.ts:8,15,20,25`. During file navigation, payload extraction, or shell use this fires continuously. It is the single largest source of wasted render work in the app.

### 2.2 The log panel renders 1,000 unmemoised rows and recompiles 1,000 regexes per line

`LogsPanel.tsx:172` maps `filteredLogs` with no virtualisation; `LogRow` (`:57`) is not memoised; the store caps at 1,000 (`logStore.ts:3`). `useShallow` at `:85-93` can never help because `logs` is a fresh array after every append (`logStore.ts:55-63`). `HighlightedText` constructs `new RegExp(...)` **per row per render** (`:28`).

`BottomPanel.tsx:40-59` additionally drills the whole array into `PanelHeaderActions`, re-rendering ~7 Radix tooltips and a dropdown per log line.

### 2.3 Zustand `persist` writes to `localStorage` synchronously on every `set()`

Verified against `zustand@5.0.14` source (`middleware.mjs:358-369`) — `api.setState` is wrapped unconditionally, with no dirty-check and no debounce.

The damaging path is payload extraction: `usePayloadEvents.ts:28-73` subscribes to `payload:progress` **unthrottled**, and each event triggers:

```
2 × new Map(...) clone  +  {...get()}  +  partialize  +  JSON.stringify  +  blocking localStorage.setItem
```

…plus ~50 selector evaluations (`PayloadDumperView.tsx:18-42` = 25 subscriptions, `usePayloadActions.ts:60-84` = 25 more). Combined with §3.3 below (thousands of progress events emitted from Rust), this is the extraction-jank mechanism.

### 2.4 `staleTime: 0` makes every window focus respawn ADB subprocesses

`App.tsx:7` sets `staleTime: 0`, which is already the library default — so it documents the wrong choice rather than fixing it. With `refetchOnWindowFocus` enabled by default, **every alt-tab refetches every mounted query**, and each query spawns an `adb`/`emulator` subprocess.

`EmulatorView.tsx:43-47` polls AVDs every 5 s with no `staleTime` — and `STALE_TIME.EMULATOR_LIST` already exists at `queries.ts:41`, unused.

### 2.5 Zero code splitting

`viewConfig.tsx:2-10` statically imports all nine views. Confirmed **zero** occurrences of `React.lazy`, `Suspense`, or dynamic `import()` in `src/`. `vite.config.ts:51` raises `chunkSizeWarningLimit` to 600, suppressing the warning that would surface this.

## 3. Performance — Rust

### 3.1 Shipped binaries are size-optimised for a CPU-bound workload

`Cargo.toml:146-152` sets `opt-level = "s"`. A `release-fast` profile with `opt-level = 3` exists at `:156-158` and **no CI or publish job uses it** (`publish.yml:147-179`). `opt-level = "s"` disables loop vectorisation and most unrolling — precisely what sha2, inflate, and the copy loops need.

### 3.2 The write path is a byte-at-a-time loop on both shipped ARM targets

`payload/io/copy.rs:83-174`, sole production caller `io/write.rs:63`:

- `copy_scalar` (`:162-169`) is `while i < len { dst[i] = src[i]; i += 1 }` — bounds-checked, one byte per iteration. Every `#[cfg(not(target_arch = "x86_64"))]` variant delegates to it (`:147-160`), and both `aarch64-pc-windows-msvc` and `aarch64-unknown-linux-gnu` ship (`publish.yml:155,179`).
- The x86 variants call `_mm256_loadu_si256` from functions **without `#[target_feature(enable = "avx2")]`**, so LLVM cannot widen or unroll them — worse code than `memcpy`.
- `copy_avx512` issues `_mm_sfence()` per call despite using ordinary (not streaming) stores. Nothing in the crate uses a non-temporal store intrinsic, so `NonTemporalWriter`'s name and doc comment are factually wrong.

`dst.copy_from_slice(src)` deletes ~90 lines of `unsafe` and is faster on every supported platform.

### 3.3 Hot-path waste

| ID | Issue | Cost | Evidence |
| --- | --- | --- | --- |
| H1 | `payload.manifest.clone()` **inside the rayon loop** — a full `DeltaArchiveManifest` (10–50 MB) cloned per partition, and **never read** by the callee | 0.2–2 GB alloc+memcpy per extraction | `crau/extract.rs:106` (callee reads only `:265,268,271`) |
| H3 | Progress emitted **per operation**; the 250 ms throttle gates only the ETA math, not `emit_progress` | 2,000–16,000 IPC events per extraction | `crau/extract.rs:410,427`; `remote/mod.rs:1024,1142`; `factory.rs:628` |
| H5 | Remote prefetch issues **sequential** 1 MiB range requests — 4,096 round-trips for 4 GiB; caps throughput at `chunk/RTT` ≈ 25 MB/s | ~164 s pure latency at 40 ms RTT | `remote/mod.rs:565-591`, `factory.rs:575-591` |
| H6 | `verify_sha256` **reopens and re-reads every output image** in a second full pass, with a redundant 64 KiB memcpy per chunk. The `hasher: Option<&mut Sha256>` parameter that would avoid this exists and is `None` at all 3 production call sites | +8 GiB of reads per typical extraction | `verify/output_file.rs:6-20`; `io/copy.rs:187` vs `extract.rs:352`, `remote/mod.rs:1012,1130` |
| H4 | Remote extract paths run `par_iter()` + blocking IO directly in `async fn` — **pins a Tokio worker for minutes**. Local paths correctly use `block_in_place` | worker starvation | `commands/payload.rs:99-116` → `remote/mod.rs:659-702,822-868` |
| M4 | OPS extractor spawns **one unbounded OS thread per partition**; cancellation checked only at partition start | 100 threads on a 100-entry OFP | `ops/extractor.rs:131-148` |

### 3.4 There is no ADB abstraction — 112 spawn sites, zero batching

Every device interaction is `Command::new(adb).output()`. No batching, no persistent shell, no connection reuse, and **three separate reimplementations** of the same exit-marker parsing (`helpers.rs:65-113`, `emulator/root.rs:111-126,1152`, `commands/files.rs:49-57`).

`helpers.rs:233-320` also re-resolves the binary path and working directory on **every** call — 4–8 syscalls (`resource_dir()`, up to 2 `exists()`, `fs::metadata`, 1–2 more `exists()`, possibly `current_dir()` and a full PATH walk) before `Command::spawn`.

The three worst consequences:

| Path | Current | Achievable |
| --- | --- | --- |
| `get_device_info` — the most-hit command in the app | **12 sequential spawns**, 0.4–1.8 s (self-documented at `device.rs:112-114`) | 1–2 spawns |
| Debloat restore | **400–500 spawns**, 12–100 s (`from_ref` on a batch-capable API) | 3–4 spawns |
| Emulator root pipeline | ~35–40 sequential spawns per run | batched |
| `list_avds` @ 5 s poll | ~48 spawns/minute while the view is open | ~8/min at 30 s |

### 3.5 Structural

`CmdResult<T> = Result<T, String>` (`lib.rs:15`) means control flow depends on **substring-matching English error text**:

```rust
let cancelled = message.to_ascii_lowercase().contains("cancelled");            // commands/payload.rs:137
error.to_string().to_ascii_lowercase().contains("extraction cancelled")        // factory.rs:264
```

Rewording any `bail!` silently changes behaviour. `payload/error.rs` exists but is `#[allow(dead_code)]`.

**Concurrency verdict:** no lock is held across an `await` anywhere — that bug class is absent. Real issues are the single-slot `PayloadCache` mutex held across a multi-GB stream (`zip/extract_entry.rs:73-93`) and silent no-op cache invalidation on a poisoned lock (`debloat/cache.rs:92`).

## 4. Design language — current state

### 4.1 It is the stock shadcn neutral theme, untouched

Every base colour is `oklch(L 0 0)` — **chroma exactly zero**. `--primary` is literally black in light mode and near-white in dark. There is no brand hue anywhere in the ramp. The only chromatic tokens are `--destructive`, `--success`, `--warning`, and an unused chart ramp.

`--chart-1..5` are defined (`global.css:98-102,206-210`) and **never referenced** — there is no chart, graph, or data visualisation anywhere in the product.

### 4.2 Primary buttons emit a black halo

`button-variants.ts:9` gives the default variant `shadow-[0_0_15px_color-mix(in_oklch,var(--primary)_50%,transparent)]`, expanding to `0_0_25px_3px` on hover. Since `--primary` is black in light mode, **every primary CTA emits a black glow on white** — it reads as a smudge, not a highlight. Destructive does the same in red (`:11`).

### 4.3 No visible page title anywhere in the application

Every view's `<h1>` is `sr-only` (all nine confirmed), and the header renders no title or breadcrumb (`Header.tsx:36-135`). The only wayfinding in the entire app is the sidebar's active-item highlight.

### 4.4 Typography

- **One family**, `"Onest"`, fetched from Google Fonts at runtime (`index.html:10-15`), explicitly permitted in CSP (`tauri.conf.json` `font-src`/`style-src`). Offline — the normal state for a device-flashing tool — the entire UI falls back to the OS sans-serif.
- **No `--font-mono` token exists**, yet `font-mono` is used in **21 files** (terminal, logs, package names, paths, serials, hashes). The app's signature feature is a terminal panel with no deliberate monospace typeface.
- **The type ramp is effectively two sizes**: 320 of 367 declarations are `text-xs` or `text-sm`. Plus **47 arbitrary sizes** bypassing the scale, including `text-[9px]` ×6 — used for the header unread badge and the debloater safety-tier chips, i.e. the two places where misreading has consequences.

### 4.6 Feedback & state

- **Determinate progress exists for exactly 1 of ~15 long operations.** Push, pull, flash, sideload, wipe, marketplace download, AVD launch/restore, and `GetDeviceInfo` all show an indeterminate toast or a button spinner. `Progress` is imported in 2 files app-wide.
- **Debloat apply — the second-most destructive batch operation — has no in-flight feedback at all** (`DebloaterTab.tsx:126-152`).
- **Toasts are the primary, often only, error surface** — 59 `toast.error` sites across 23 files; `handleError` also writes to a log panel that is closed by default. `richColors` overrides the app's own semantic tokens with sonner's palette.
- **Skeletons are effectively unimplemented** — one feature site with two bars; `SidebarMenuSkeleton` is defined and never rendered. Lists with known fixed row heights use full-pane spinners.
- **No-device state is "silently disabled buttons" in 5 of 9 views.** Marketplace has **zero** device awareness — `install.ts:11` resolves the serial at click time and happily passes `null`. `"No packages found."` is shown when there is no device (`InstalledPackageList.tsx:158`), which reads as "this device is empty."
- `ActionButton` **disables every button in Utilities for 2 s after any successful click** because `sentAction` participates in the global-disable predicate (`ActionButton.tsx:41-42`).
- **Zero onboarding.** No first-run, tour, help, or shortcut reference anywhere.

## 5. What is genuinely good — preserve this

1. **Token architecture.** 60+ semantic CSS variables, full light/dark parity, `oklch` throughout, `color-mix`-derived tints. Exactly 7 hard-coded colours in 23.6k lines. Keep the *architecture*; replace the values.
2. **Device-status token family** — one source of truth for bg/fg/border per connection state via a single helper (`deviceStatus.ts:75-78`). Fix `recovery`/`adb` being visually identical; keep the pattern.
3. **Bottom-panel resize** (`useBottomPanelResize.ts:21-66`) — DOM writes during drag, single commit on mouseup, RAF-throttled, cursor overlay, real keyboard resize, correct `role="separator"` ARIA. Genuinely well built.
4. **File Explorer's error taxonomy** (`FileExplorerTablePane.tsx:131-152`) — three distinct actionable states, each with icon, headline, and next step. This is the model every other view should follow.
5. **File Explorer keyboard support** (`useFileExplorerKeyboardShortcuts.ts`) — comprehensive, view-scoped, input-aware, and surfaced in the context menu.
6. **Payload dumper progress model** — real per-partition byte percentage with throughput, working cancel, and `RemoteLoadProgressCard` which documents its own indeterminacy and escalates copy at 20 s / 45 s. The best long-operation UX in the app; generalise it.
7. **The AVD root wizard's "smart gate, not a dead end"** (`EmulatorRootTab.tsx:31-73`) — when blocked it explains why, offers both remedies inline, and says which to pick. Every disabled state should work like this.
8. **Batch-confirmation dialogs** (`InstalledPackageList.tsx:239-284`, `DeleteDialog.tsx:48-69`) — list actual items, show counts, real disclaimers.
9. **Virtualisation with correct ARIA** in three lists — `getItemKey` supplied, full `role="option"`/`aria-selected`/`tabIndex` on every virtual row. Rare and correct.
10. **Per-view error boundaries with working retry**, keyed per view (`ViewContent.tsx:43`).
11. **Real performance discipline already present:** `LazyMotion … strict` with zero `motion` imports across 5 sites; one global 30 s device poll; no barrel files (zero `index.ts` under `src/`); `lucide-react` correctly named-imported across 88 files; context values memoised; event listeners correctly disposed; no selectors returning fresh literals.
12. **`tsconfig.json` is exceptionally strict** — `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `verbatimModuleSyntax`, `noImplicitReturns`.
13. **`src/test/frontendArchitecture.test.ts` is a real fitness function** — enforces IPC containment, folder boundaries, and a 300-line cap.
14. **Rust path-safety and clippy discipline** — `-D warnings` clean, adversarial traversal tests, `#[lints]` with `unwrap_used`/`expect_used` denied outside tests.

## 6. Test coverage gap — sequencing risk

~28 of ~197 frontend modules are touched by tests (**~14%**). No coverage thresholds; `bun run check` never runs `--coverage`. The two largest business-logic files — `useFileExplorerViewModel.ts` (462 lines) and `desktop/backend.ts` (440 lines) — have zero direct tests, and `backend.ts` is systematically `vi.mock`'d away. `LogsPanel`, `ShellPanel`, `DropZone`, `MainLayout`, and all 11 file-explorer hooks are untested.

**This matters:** the highest-severity frontend fixes (§2.1, §2.2, §2.3, §2.6) all land in untested code. Characterisation tests come first.
